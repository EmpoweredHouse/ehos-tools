# T-04 · A generated project follows eh-os-contract's `main` while eh-os-contract tags no release

## Context and problem statement

`eh_os_contract` and `eh_os_contract_auth`, the contract engine and the credential verifier, are not
on Hex and tag no release: eh-os-contract's packages are at `0.3.0-dev` and `0.1.0-dev`, and its
last tag is `v0.2.1`. Up to 0.4.0, `ehos_app` pinned both to one commit, moved only when `ehos_app`
released, as it pins its other git dependencies
([T-02](0002-a-project-takes-a-later-ehos-app-by-running-the-installer-again.md)).

The pin fell behind faster than `ehos_app` released. The field test that reported
[#36](https://github.com/EmpoweredHouse/ehos-tools/issues/36) found its project on an engine that
predated aggregate lifecycles and most of what a contract written today uses, and `ehos_app` 0.4.0's
pin, `da9f56f`, is about 200 commits behind eh-os-contract's `main` days after it was set. Nothing
told the project: `mix hex.outdated` does not see a git dependency, and `mix ecto.setup` and
`mix precommit` pass on an old engine
([#39](https://github.com/EmpoweredHouse/ehos-tools/issues/39)). The application is then written
against an engine EHOS itself has moved on from.

## Decision drivers

- An application is written against the engine EHOS is built on today, while that engine is in
  development.
- A project builds the same way on every machine until its developer chooses to move.
- A developer can move to the latest engine with one standard command.

## Considered options

1. Follow `main`: `branch: "main"` in `mix.exs`, the commit held by `mix.lock`
2. Keep pinning a commit, moved by more frequent `ehos_app` releases
3. Keep pinning a commit, and add a check (`ehosctl` or `mix precommit`) that reports the pin is
   behind `main`

## Decision outcome

Chosen option: **"Follow `main`"**, because it is the only option where a new project gets the
current engine without a release of `ehos_app` in between, and Mix already gives what the other
two would have to build: `mix.lock` records the commit, so a project is reproducible, and
`mix deps.update eh_os_contract eh_os_contract_auth` moves it. The installer moves a project on a
commit an earlier version pinned (`da9f56f` included) to `main`, asking first unless `--yes`, and
leaves one on any other commit or branch, which its developer chose. Once eh-os-contract releases
0.3.0, the template pins its tag instead, and this record is superseded.

### Consequences

- Good, because `ehosctl init` generates against the engine of that day, not of the last
  `ehos_app` release.
- Good, because moving to the latest engine is `mix deps.update`, which every Elixir developer
  knows, and the generated `ARCHITECTURE.md` says so under "Known limitations".
- Bad, because one `ehosctl` release no longer means one template for the engine: two projects
  generated by the same binary on different days get different commits of eh-os-contract. The rest
  of the template stays pinned (`Ehosctl.Template`).
- Bad, because a change on eh-os-contract's `main` that the installer does not expect (a renamed
  module, a new verifier migration version, a requirement past `~> 0.3.0-dev`) breaks a new
  project's first compile, and CI's `e2e` job here, until `ehos_app` follows it. Mitigated by
  `e2e` running on every pull request and push to `main`, which catches it on the next change,
  and by the requirements in `mix.exs`, which fail loudly at compile time rather than quietly.
- Bad, because `mix deps.update eh_os_contract` alone moves the engine without the verifier, and
  the verifier names the engine by git without a ref. The docs name both packages together.
- Neutral: the installer's sign-in still needs at least `da9f56f`; a project on an older commit of
  its own choosing is warned with that commit.

### Confirmation

`Mix.Tasks.EhosApp.InstallTest`: "adds the engine and the credential verifier from eh-os-contract's
main" pins `branch: "main"` for both, and "moves both packages from the commit 0.4 pinned to main"
pins the move. The `e2e` job in [`.github/workflows/ci.yml`](../../.github/workflows/ci.yml)
compiles a generated project against `main` on four platforms.

## Pros and cons of the options

### Follow `main`

- Good, because nothing has to be released for a project to get the current engine.
- Good, because `mix.lock` keeps a project reproducible, and `mix deps.update` moves it.
- Bad, because a breaking change on `main` reaches a new project before `ehos_app` adapts.

### Pin a commit, released more often

- Good, because one `ehosctl` release stays exactly one template.
- Bad, because the pin lags by however long releases take, and it lagged by hundreds of commits
  between 0.2.0 and 0.4.0.
- Bad, because a project still learns of nothing between releases.

### Pin a commit, with a check that reports it behind

- Good, because the project is told.
- Bad, because it is code to write and maintain that reads eh-os-contract's `main` over the network
  from a developer's machine, and from CI, where the repository is private and needs a token.
- Bad, because being told is not being moved: the developer still edits the `ref:` by hand.

## More information

Revisit when eh-os-contract tags 0.3.0 (the comment above `@eh_os_contract_branch` in
`Mix.Tasks.EhosApp.Install` says the same), or when `main` breaks generated projects more often
than a release of `ehos_app` would.
