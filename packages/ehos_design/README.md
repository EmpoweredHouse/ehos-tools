# ehos_design

The EmpoweredHouse design system, as files a Phoenix application builds its styles from: the
design system's tokens, a layer that maps them to Tailwind CSS 4 and daisyUI 5, and the two fonts.
It is the default look of an application generated by [`ehosctl init`](../ehosctl/README.md), and
the look of the [EHOS](https://github.com/EmpoweredHouse/eh-os) console and of `eh_os_contract`'s
dashboard.

It is a default, not a rule. An application may override any token, or drop the package and bring
its own look; [Changing the look](#changing-the-look) says how.

Why a package rather than a copy in each project is
[eh-os D-72](https://github.com/EmpoweredHouse/eh-os/blob/main/docs/adr/0072-the-design-system-is-a-library-ehos-design-kept-in-ehos-tools.md).

## What is in it

| File | What | Who changes it |
| --- | --- | --- |
| `priv/css/colors_and_type.css` | The tokens: colour, type, radii, motion, focus, a dark theme and a light one | Nobody by hand. A refresh from Claude Design replaces it, and a test fails if it differs from `SOURCE.md` |
| `priv/css/SOURCE.md` | Where the tokens came from, the one change made to them, and their hash | The refresh |
| `priv/css/ehos_design.css` | The layer for Tailwind CSS 4 and daisyUI 5: imports the tokens, maps them to utilities (`bg-surface-1`, `text-fg-secondary`, `border-line-faint`, …) and to one daisyUI theme, declares the fonts, and brings daisyUI's components to the design system's rules | Anyone, in a pull request. It refers to the tokens and never redefines one, and a test checks that |
| `priv/static/ehos_design/fonts/` | Albert Sans and JetBrains Mono at 400 and 500, `latin` and `latin-ext`, as WOFF2, with their SIL Open Font License texts | A pull request that changes `SOURCE.md` too |

The design system selects its theme by `data-theme` on `<html>`: dark by default, light under
`prefers-color-scheme: light` or `data-theme="light"`, either pinned by `data-theme`. That is the
attribute the theme toggle Phoenix 1.8 generates already sets.

Its rules, the ones the tokens alone do not carry: one accent (lime), weights 400 and 500 only,
hairline borders, no drop shadows, the lime focus ring. The layer applies them to daisyUI's buttons,
inputs and checkboxes, so the `core_components.ex` Phoenix generates follows them unchanged.

## Using it

The package is not on Hex. Take it from this repository at a tag:

```elixir
{:ehos_design,
 github: "EmpoweredHouse/ehos-tools", sparse: "packages/ehos_design", tag: "ehos_design-v0.1.0"}
```

A `sparse:` dependency keeps its subdirectory, so the files are under
`deps/ehos_design/packages/ehos_design/priv/`.

### With Tailwind and daisyUI, as Phoenix 1.8 generates them

In `assets/css/app.css`, import the layer right after Tailwind, keep daisyUI's own themes off, and
remove the two `daisyui-theme` blocks Phoenix writes:

```css
@import "tailwindcss" source(none);
@import "../../deps/ehos_design/packages/ehos_design/priv/css/ehos_design.css";

@plugin "../vendor/daisyui" {
  themes: false;
}
```

Serve the fonts from the application's own origin, in the endpoint, beside Phoenix's
`Plug.Static`:

```elixir
plug Plug.Static,
  at: "/",
  from: {:ehos_design, "priv/static"},
  gzip: false,
  only: ~w(ehos_design)
```

The layer names them as `/ehos_design/fonts/<file>.woff2`, and loads nothing from another origin, so
it works under a `Content-Security-Policy` of `default-src 'self'`.

### With plain CSS, or a build of your own

`priv/css/colors_and_type.css` needs nothing but a browser. Import it, or bundle it with esbuild,
declare the fonts with `@font-face` (the layer's declarations can be copied), and serve them or
copy them into your own static files. A package that commits its built assets, as
`eh_os_contract_web` does, can depend on `ehos_design` for its build alone, with
`only: :dev, runtime: false`, so its own hosts never fetch it.

## Changing the look

- **One token, or a few.** Override it on `:root` after the import, in a section of your own:

  ```css
  :root {
    --lime: #7dd3fc;
  }
  ```

  The tokens are in the `base` layer, so an unlayered rule wins. Do it for the light theme too, under
  `[data-theme="light"]` and `@media (prefers-color-scheme: light)`, if the token differs there.
- **A look of your own.** Remove the import, turn daisyUI's themes back on (or add your own
  `daisyui-theme`), and remove the `Plug.Static` for the fonts. Nothing else in the application
  depends on the package.
- **The design system itself.** It is made in Claude Design and shared by a family of products, so
  this repository never writes to it. Ask in an issue: a maintainer takes it to the design system,
  and it arrives with the next refresh.

## Refreshing the tokens

The tokens are refreshed on request, in one direction, from the design-system project that
`SOURCE.md` names. With Claude Code and the Claude Design MCP server, the `sync-design-system` skill
of this repository (`.claude/skills/sync-design-system/`) does every step below. Without it, a
maintainer with access to the project does them by hand, from the file as Claude Design exports it:

1. Compare the file's etag in Claude Design with the one in `SOURCE.md`. If it is the same, the copy
   is current.
2. Take the file whole, and check that its size in bytes and lines is what Claude Design reports.
3. Remove the Google Fonts `@import` line, and nothing else. If the file now loads anything else
   from another origin, or names fonts other than Albert Sans and JetBrains Mono at 400 and 500,
   stop: that needs a decision, and fonts to be added here.
4. Diff the old copy against the new one, and list the tokens added, removed and changed in each
   theme. A token the layer uses that is removed or renamed is handled in the layer in the same
   change, and is a breaking change for every application that uses the token.
5. Replace `priv/css/colors_and_type.css`, and rewrite `SOURCE.md`: the new etag, the date, the
   SHA-256 and size as published, and the SHA-256 as committed.
6. Run `mix check`, add the change to `CHANGELOG.md`, and raise the version: patch for changed
   values, minor for added tokens, major for removed or renamed ones.
7. Once merged, tag the merge commit `ehos_design-vX.Y.Z`. The consumers take it by raising their
   dependency.

## Development

```sh
mix check
```

Formatting, compilation with warnings as errors, and the tests. The tests check the tokens against
`SOURCE.md`, that nothing names another origin, that the layer never redefines a token, and that
every font it names is in the package.
