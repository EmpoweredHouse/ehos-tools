# ehos_design

The EmpoweredHouse design system for Phoenix applications: the design's tokens (colour, type,
radii, motion) as CSS custom properties, a layer that maps them to Tailwind CSS 4 and daisyUI 5,
the two fonts, a few components for Phoenix LiveView, and the layout of a mailed message.

It is the look of [EHOS](https://github.com/EmpoweredHouse/eh-os)'s console, of
`eh_os_contract`'s dashboard, and, by default, of every application
[`ehosctl init`](https://github.com/EmpoweredHouse/ehos-tools/blob/main/packages/ehosctl/README.md)
generates, whose template, `ehos_app`, installs it. It is a default, not a rule: an application may
override any token, or drop the package and bring its own look
([Changing the look](#changing-the-look)).

Why the design system is a package rather than a copy in each project is
[eh-os D-72](https://github.com/EmpoweredHouse/eh-os/blob/main/docs/adr/0072-the-design-system-is-a-library-ehos-design-kept-in-ehos-tools.md);
why it also carries components is
[eh-os D-86](https://github.com/EmpoweredHouse/eh-os/blob/main/docs/adr/0086-the-design-system-s-source-holds-component-stylesheets-and-ehos-design-ships-the-components-built-on-them.md).

## What is in it

| Part | What it is for | Where |
| --- | --- | --- |
| The tokens | Every colour, size and duration the design uses, in a dark theme and a light one | `priv/css/colors_and_type.css` |
| The components' look | One stylesheet per component, written on the tokens alone | `priv/css/components/` |
| The layer for Tailwind and daisyUI | Imports the two above, maps the tokens to utilities (`bg-surface-1`, `text-fg-secondary`, `border-line-faint`, …) and to one daisyUI theme, declares the fonts, and brings daisyUI's own components to the design's rules | `priv/css/ehos_design.css` |
| The fonts | Albert Sans and JetBrains Mono at 400 and 500, `latin` and `latin-ext`, as WOFF2, with their licences | `priv/static/ehos_design/fonts/` |
| The icon | The icon of EmpoweredHouse for a browser tab, a bookmark and a phone's home screen, as SVG, ICO and PNG | `priv/static/ehos_design/icons/` |
| The components | `EhosDesign.Components`: a picker, a combobox, an outcome card and a badge, as LiveView function components rendering the components' classes, with the script their keyboard needs | `lib/ehos_design/components.ex` |
| The mail | `EhosDesign.Mail`: a message's HTML part and plain-text part, from the same words, styled from the light theme | `lib/ehos_design/mail.ex` |

The tokens and the components' look are copies of a design made elsewhere, and are never edited
here ([Where the design comes from](#where-the-design-comes-from)). Everything else is ordinary
code, changed in a pull request like any other.

The design's rules, the ones the tokens alone do not carry: one accent (lime), weights 400 and 500
only, hairline borders, no drop shadows, the lime focus ring. The layer applies them to daisyUI's
buttons, inputs, checkboxes and badges, so the `core_components.ex` Phoenix generates follows them
unchanged.

The theme is chosen by `data-theme` on `<html>`: dark by default, light under
`prefers-color-scheme: light` or `data-theme="light"`, and either one pinned by `data-theme`. That
is the attribute the theme toggle Phoenix 1.8 generates already sets.

## Depending on it

It is released by tags, `ehos_design-vX.Y.Z`, each with a GitHub release whose notes are that
version's section of `CHANGELOG.md`. It is not on Hex: a project takes it from this repository's
subdirectory, at the commit a release's tag names, with that release's version beside it:

```elixir
{:ehos_design, "~> 0.4.1",
 github: "EmpoweredHouse/ehos-tools",
 sparse: "packages/ehos_design",
 ref: "<the commit ehos_design-v0.4.1 names>"}
```

The commit, not the tag, since a tag can be moved. Mix checks the version requirement when the
project compiles, not at `deps.get`, so a commit of another minor version fails there. To find a
release's commit:

```sh
git ls-remote https://github.com/EmpoweredHouse/ehos-tools \
  'refs/tags/ehos_design-vX.Y.Z' 'refs/tags/ehos_design-vX.Y.Z^{}'
# an annotated tag prints two lines: the commit is the one ending in ^{}; a lightweight tag
# prints one, which is the commit
```

A `sparse:` dependency keeps its subdirectory, so the files are under
`deps/ehos_design/packages/ehos_design/priv/`. The package needs Phoenix LiveView 1.1 or later,
which it depends on.

## Using it

An application generated by `ehosctl init` has the styles, the fonts with their preloads, the
components' hook and their `@source` already; it imports the components itself where it uses
them, and those added after the version it depends on come with a newer one (`CHANGELOG.md` says
which). The steps below are what any other Phoenix 1.8 application does, from its
`assets/css/app.css`, its endpoint, its root layout and its `assets/js/app.js`.

### Styles, with Tailwind and daisyUI

In `assets/css/app.css`, import the layer right after Tailwind's own import, keep daisyUI's themes
off (`themes: false`, as Phoenix writes it), and remove the two `daisyui-theme` blocks Phoenix
writes, which would set daisyUI's colours over the layer's:

```css
@import "tailwindcss" source(none);
@import "../../deps/ehos_design/packages/ehos_design/priv/css/ehos_design.css";
```

### Fonts

The layer names the fonts as `/ehos_design/fonts/<file>.woff2`, on the application's own origin,
and loads nothing from another one, so it works under a `Content-Security-Policy` of
`default-src 'self'`. Serve them in the endpoint, beside Phoenix's `Plug.Static`:

```elixir
plug Plug.Static,
  at: "/",
  from: {:ehos_design, "priv/static"},
  gzip: false,
  only: ~w(ehos_design),
  cache_control_for_etags: "public, max-age=86400",
  headers: %{
    "x-content-type-options" => "nosniff",
    "content-security-policy" => "default-src 'none'; style-src 'unsafe-inline'; sandbox"
  }
```

The fonts' paths carry no version, so they are cached for a day and revalidated by their ETag
after that, rather than on every page load. The same plug serves the icon, an SVG on the
application's own origin. The two headers stop a browser that opens the SVG as a page from
reading it as another type or running anything in it. A font or an image that a page loads
ignores the policy.

Preload the two faces nearly all text is set in, in the root layout's `<head>`, before the
stylesheet:

```heex
<link
  rel="preload"
  href="/ehos_design/fonts/albert-sans-latin-400-normal.woff2"
  as="font"
  type="font/woff2"
  crossorigin
/>
<link
  rel="preload"
  href="/ehos_design/fonts/albert-sans-latin-500-normal.woff2"
  as="font"
  type="font/woff2"
  crossorigin
/>
```

Without them a browser asks for a font only once it has parsed the stylesheet and laid out text
in it, so a first visit shows the fallback (`-apple-system`, `"Helvetica Neue"`) and then reflows
into Albert Sans. Body text is set at 400; bold text, buttons, table headers and the title classes
(`.eh-display`, `.eh-section-title`, `.eh-h3`) at 500. A page with none of those preloads 500 for
nothing, about 10 KB and a console warning, which is the price of every other page drawing them
right the first time. `crossorigin` is required even on the same origin: fonts are fetched in CORS
mode, and a preload without it is fetched twice. The other faces (`latin-ext`, JetBrains Mono) are
left to load on demand, since a preload a page does not use costs a request and a console
warning.

### The icon

The `Plug.Static` that serves the fonts serves the icon too, under `/ehos_design/icons/`. Name it
in the root layout's `<head>`:

```heex
<link rel="icon" href="/ehos_design/icons/favicon.ico" sizes="32x32" />
<link rel="icon" href="/ehos_design/icons/favicon.svg" type="image/svg+xml" />
<link rel="apple-touch-icon" href="/ehos_design/icons/apple-touch-icon.png" />
```

A browser that reads SVG icons uses the second line. Other browsers use the ICO, at 16, 32 or 48
pixels. A phone uses the PNG, at 180 pixels, for its home screen. To give an application an icon of
its own, put its files in the application's `priv/static/` and point these three lines at them.

The icon is a mark of EmpoweredHouse, and the package's licence does not cover it. EmpoweredHouse
lets the EHOS console, and an application generated with `ehosctl init`, show it as their browser
icon. Remove the `favicon.ico` that Phoenix puts in `priv/static/`, and its name in
`static_paths/0`, so that no address still serves that icon. A browser keeps an icon for a day or
more, so a changed icon shows after that.

### Without Tailwind

`priv/css/colors_and_type.css` needs nothing but a browser. Import it, or bundle it with esbuild,
declare the fonts with `@font-face` (the layer's declarations can be copied), and serve them or
copy them into your own static files. A package that commits its built assets, as
`eh_os_contract`'s dashboard does, can depend on `ehos_design` for its build alone, with
`only: :dev, runtime: false`, so the projects that depend on it never fetch it.

### The components

`EhosDesign.Components` has four function components:

- `EhosDesign.Components.picker/1`, a button that opens a list to choose one option from;
- `EhosDesign.Components.combobox/1`, a text field whose list shows what the application found
  for what is typed;
- `EhosDesign.Components.outcome/1`, a card that says how something ended: a mark (a lime check,
  or a coral cross for `kind={:error}`), a title, one sentence and an optional hint. A page that
  shows only that puts it in `<main>` under `<body class="eh-outcome-page">`, after a
  `<header class="eh-outcome-header">`;
- `EhosDesign.Components.badge/1`, a short label for a state: `variant={:live}`, with a lime dot,
  for what is in force, `:neutral` (the default) for meta, `:error` for what failed. Its classes,
  `.eh-badge` and its variants, are in the layer, since the design has no stylesheet of its own
  for it, and daisyUI's `.badge`, `badge-success` and `badge-error` look the same.

The picker and the combobox are the listbox's two controls. Each option is a title and an optional
subtitle, optionally in groups. Both follow the WAI-ARIA Authoring Practices' combobox patterns:
the focus stays on the control, the arrow keys move through the list, Enter chooses, and Escape
closes it. A choice sets a hidden input and dispatches `input` on it, so the form's `phx-change`
receives it like any other field. The application keeps what is offered and what is chosen, and
passes the chosen value back, as it does for any input. The module's documentation has the keys
and every attribute.

Import the module where the application's components are, such as `html_helpers` in
`lib/my_app_web.ex`:

```elixir
import EhosDesign.Components
```

A host with a `badge/1` of its own, there or in its `CoreComponents`, removes it, or imports the
package's with `except: [badge: 1]`: otherwise `<.badge>` is ambiguous, and does not compile.

Add their hook to the `LiveSocket` in `assets/js/app.js`. The hook is colocated, so LiveView's
compiler writes it under the build's `phoenix-colocated/ehos_design`, beside the application's
own:

```js
import {hooks as colocatedHooks} from "phoenix-colocated/my_app"
import {hooks as designHooks} from "phoenix-colocated/ehos_design"

const liveSocket = new LiveSocket("/live", Socket, {
  hooks: {...colocatedHooks, ...designHooks},
  // …
})
```

Their stylesheets come with the layer. The components also use `fieldset`, `label` and a margin
utility around the control, as Phoenix's `<.input>` does; so that Tailwind finds them even where
the application does not use them itself, name the package's templates as a source in
`assets/css/app.css`:

```css
@source "../../deps/ehos_design/packages/ehos_design/lib";
```

### Mail

`EhosDesign.Mail` renders a message in the one layout EHOS mails in
([eh-os D-122](https://github.com/EmpoweredHouse/eh-os/blob/main/docs/adr/0122-ehos-s-mail-is-written-in-heex-inlined-by-premailex-styled-from-ehos-design-s-tokens-and-sent-with-a-plain-text-part.md)):
the brand as text, a panel with the message, and a footer, on the light theme's tokens. It returns
two strings, the HTML part and the plain-text part; the sender puts them in its own envelope, with
Swoosh or through EHOS's mail API, which sends an application's HTML as written. It needs none of
the setup above.

A message is its words, and its body is a list of blocks given as data, so both parts are rendered
from the same blocks and say the same thing:

```elixir
message = %{
  lang: "en",
  brand: "Office",
  context: "Accounting",              # optional, beside the brand in small uppercase
  subject: "Documents for November",
  preview: "Two documents, by 10 November.",
  label: "Request",                   # optional, above the heading
  heading: "Documents for November",
  body: [
    {:paragraph, "Please send us:"},
    {:rows, [{"Bank statements", "by 10.11.2026"}, {"Cost invoices", "by 10.11.2026"}]},
    {:action, %{label: "Open", url: "https://office.example.test/x", hint: "If the button does not work, open this link:"}},
    {:notice, "The link works for 7 days."}
  ],
  footer: ["Office, accounting"]
}

EhosDesign.Mail.html(message)  # the HTML part
EhosDesign.Mail.text(message)  # the plain-text part
```

| Block | HTML | Text |
| --- | --- | --- |
| `{:paragraph, text}` | A paragraph | The text |
| `{:rows, [{item, detail}]}` | Each item with its detail on the right, between hairlines | `- item: detail`, a line each |
| `{:action, %{label:, url:, hint:}}` | A lime button leading to an absolute `http`, `https` or `mailto` link in ASCII, a host in punycode and a path percent-encoded (any other raises), then `hint` (optional) and the link written out | `label:` and the link |
| `{:notice, text \| [text]}` | Small type after a divider | The lines |

Any other block raises `ArgumentError`, as does a message missing its words. A block a sender
needs that is not here, a table with columns or a callout, is added here with its first sender, as
a minor version, so it is checked in mail programs once for everyone.

Every value is plain text, escaped, so a name cannot change the markup. The HTML is written as
tables with `bgcolor`, a fixed width for Outlook in its conditional comments, and the narrow
screen's rules in `<style>`, every other rule moved into each element's `style` by `premailex`.
It fetches nothing when opened: no image, font or stylesheet, so a reader without Albert Sans and
JetBrains Mono sees the stacks' fallbacks. A message with thirty rows is about a quarter of the
size past which Gmail clips one; each row adds about 600 bytes, so a list of more than about 150
rows is clipped, its notice and footer hidden behind a link.

## Changing the look

- **One token, or a few.** Override it on `:root` after the import, in a section of your own:

  ```css
  :root {
    --lime: #7dd3fc;
  }
  ```

  The tokens are in the `base` layer, so an unlayered rule wins. A token that differs between the
  themes is overridden in the four places the tokens set it, in their order: on `:root`, under
  `@media (prefers-color-scheme: light)` on `:root`, then under `[data-theme="light"]` and
  `[data-theme="dark"]`, the last two after the media query so that they win by order. Leaving
  out the last one shows the light value to a person who pinned dark on a light system.
- **A look of your own.** Remove the import, turn daisyUI's themes back on (or add your own
  `daisyui-theme`), remove the `Plug.Static` for the fonts and the icon, the fonts' preloads, the
  three icon links, the `@source` of the package's templates, and the import of its hooks and
  `...designHooks` in `assets/js/app.js`, and remove the dependency. Whatever uses the design's
  classes or tokens by name changes with it, such as the example page an application generated by
  `ehosctl init` has at `/design-system`. In such an application, keep the comment above the import,
  as it says: it tells `ehos_app`'s installer not to add the design system back.
- **The design itself.** Ask in an issue here;
  [Where the design comes from](#where-the-design-comes-from) says why it is not changed in this
  repository.

## Where the design comes from

The design system is made in Claude Design, Anthropic's tool for designing with Claude, in a
design-system project shared by a family of EmpoweredHouse products. The tokens and the
components' stylesheets in `priv/css/` are copies of that project's files, kept here so that
nothing that uses them needs Claude Design.

They are never edited here. An edit made here would be lost at the next refresh and would make
this copy differ from what the other products use, so a token or a component's look an
application needs changed is asked for in an issue: a maintainer takes it to the design system,
and it arrives here with the next refresh. A maintainer may have an agent make the change there,
for named files, conditional on each file's etag, but never as part of a refresh (eh-os D-86).

[`priv/css/SOURCE.md`](https://github.com/EmpoweredHouse/ehos-tools/blob/main/packages/ehos_design/priv/css/SOURCE.md)
records, for each file, the project it came from, its etag there, when it was taken, and its
SHA-256. The tests fail when a file no longer matches its hash, so a hand edit cannot pass the
gate. The one change made on copying is in the tokens: the Google Fonts `@import` is removed,
since the fonts are in this package and the application serves them.

## Refreshing the design system

A refresh is made on request, in one direction: from Claude Design to here, never back. With Claude
Code and the Claude Design MCP server, this repository's `sync-design-system` skill
(`.claude/skills/sync-design-system/`) does every step below. Without them, a maintainer with
access to the project does them by hand, from each file as Claude Design exports it:

1. Compare each file's etag in Claude Design with the one in `SOURCE.md`. A file whose etag is the
   same is current. A stylesheet under `components/` that `SOURCE.md` does not list is a new
   component.
2. Take each changed file whole, and check that its size in bytes and lines is what Claude Design
   reports. Whatever is copied by hand or by a tool, take it twice and compare the two byte for
   byte: a size does not catch one character changed for another.
3. In `colors_and_type.css`, remove the Google Fonts `@import` line, and nothing else. A
   component's stylesheet is taken unchanged. If a file now loads anything from another origin,
   or names fonts other than Albert Sans and JetBrains Mono at 400 and 500, stop: that needs a
   decision, and fonts to be added here.
4. Diff each old copy against the new one. For the tokens, list those added, removed and changed
   in each theme; for a component, the classes and states. A token the layer uses, or a class
   `EhosDesign.Components` renders, that is removed or renamed is handled in the same change, and
   is a breaking change for every application that uses it.
5. Replace the copies under `priv/css/`, and rewrite `SOURCE.md`: for each, the new etag, the
   date, the SHA-256 and size as published, and, for the tokens, the SHA-256 as committed. A new
   component's stylesheet is imported by `ehos_design.css` and rendered by a component here.
   Keep `SOURCE.md`'s "Icon" section as it is: the icon is not part of a refresh.
6. Run `mix check`, and add the change to `CHANGELOG.md` under `## [Unreleased]`: what it asks
   of the next release is a patch for changed values, a minor version for added tokens,
   components, classes or states, and a major one for removed or renamed ones, whose line starts
   with `**Breaking:**`. The version in `mix.exs` stays as it is: it changes only in a release's
   pull request ([releases](https://github.com/EmpoweredHouse/eh-os/blob/main/docs/releases.md)).
7. A font is replaced under a new file name, never in place: its path carries no version, and a
   browser keeps the old file for a day.
8. Once merged, it reaches the applications with the next release: a pull request of its own sets
   the version and moves the `Unreleased` lines under it, and the tag `ehos_design-vX.Y.Z` on its
   merge commit publishes it. The applications take it by raising their dependency.

## Working on it

```sh
mix browser.setup   # once per machine, with Node and npm installed: Playwright and its browser
mix check
```

`mix check` is the gate: the dependency audit (it needs the network), formatting, compilation with
warnings as errors, Credo, the tests with warnings as errors, Dialyzer, and this reference, built
with ExDoc with warnings as errors (`mix docs` builds it into `doc/`).

The tests check the tokens, the components' stylesheets and the fonts against the hashes in
`SOURCE.md`, that nothing names another origin, that every token the layer uses is defined and
none is redefined, that every font it names is in the package, that the icons are the files
`SOURCE.md` records, and that nothing but the fonts, their licences and the icons is where a host
serves them from. They render each component and check its roles,
states and classes, and a browser test (`test/ehos_design/components_browser_test.exs`) drives a
page with the picker and the combobox through the keyboard and the pointer, on a LiveView served
from `test/support/browser/`. The mail's tests render each block in both parts, and check that a
value cannot change the markup.

How code, tests and commits are written here is the repository's
[CONTRIBUTING.md](https://github.com/EmpoweredHouse/ehos-tools/blob/main/CONTRIBUTING.md).
