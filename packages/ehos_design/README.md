# ehos_design

The EmpoweredHouse design system, as files a Phoenix application builds its styles from: the
design system's tokens, a layer that maps them to Tailwind CSS 4 and daisyUI 5, the two fonts, and
the design system's application components for Phoenix LiveView.
It is meant to be the default look of an application generated by
[`ehosctl init`](../ehosctl/README.md), once `ehos_app` installs it, and the look of the
[EHOS](https://github.com/EmpoweredHouse/eh-os) console and of `eh_os_contract`'s dashboard, which
style themselves from copies of these files today and move to the package next.

It is a default, not a rule. An application may override any token, or drop the package and bring
its own look; [Changing the look](#changing-the-look) says how.

Why a package rather than a copy in each project is
[eh-os D-72](https://github.com/EmpoweredHouse/eh-os/blob/main/docs/adr/0072-the-design-system-is-a-library-ehos-design-kept-in-ehos-tools.md);
why it also carries components is
[eh-os D-86](https://github.com/EmpoweredHouse/eh-os/blob/main/docs/adr/0086-the-design-system-s-source-holds-component-stylesheets-and-ehos-design-ships-the-components-built-on-them.md).

## What is in it

| File | What | Who changes it |
| --- | --- | --- |
| `priv/css/colors_and_type.css` | The tokens: colour, type, radii, motion, focus, a dark theme and a light one | Nobody by hand. A refresh from Claude Design replaces it, and a test fails if it differs from `SOURCE.md` |
| `priv/css/SOURCE.md` | Where the tokens came from, the one change made to them, and their hash | The refresh |
| `priv/css/components/` | The look of each application component, one stylesheet each, on the tokens alone | Nobody by hand. A refresh from Claude Design replaces it, and a test fails if it differs from `SOURCE.md` |
| `lib/ehos_design/components.ex` | `EhosDesign.Components`: the components as LiveView function components, rendering those stylesheets' classes, with the hook their keyboard needs | Anyone, in a pull request |
| `priv/css/ehos_design.css` | The layer for Tailwind CSS 4 and daisyUI 5: imports the tokens, maps them to utilities (`bg-surface-1`, `text-fg-secondary`, `border-line-faint`, …) and to one daisyUI theme, declares the fonts, and brings daisyUI's components to the design system's rules | Anyone, in a pull request. It refers to the tokens and never redefines one, and a test checks that |
| `priv/static/ehos_design/fonts/` | Albert Sans and JetBrains Mono at 400 and 500, `latin` and `latin-ext`, as WOFF2, with their SIL Open Font License texts | A pull request that changes `SOURCE.md` too |

The design system selects its theme by `data-theme` on `<html>`: dark by default, light under
`prefers-color-scheme: light` or `data-theme="light"`, either pinned by `data-theme`. That is the
attribute the theme toggle Phoenix 1.8 generates already sets.

Its rules, the ones the tokens alone do not carry: one accent (lime), weights 400 and 500 only,
hairline borders, no drop shadows, the lime focus ring. The layer applies them to daisyUI's buttons,
inputs and checkboxes, so the `core_components.ex` Phoenix generates follows them unchanged.

## Using it

The package is not on Hex. Take it from this repository at the commit a release's tag names, with
that release's version beside it:

```elixir
# ehos_design-v0.1.0
{:ehos_design, "~> 0.1.0",
 github: "EmpoweredHouse/ehos-tools",
 sparse: "packages/ehos_design",
 ref: "a65b9c86d920b5566f1c085b2286a44da77505c9"}
```

The commit, not the tag, since a tag can be moved. Mix checks the requirement when the project
compiles, not at `deps.get`, so a commit of another minor version fails there. To find a
release's commit:

```sh
git ls-remote https://github.com/EmpoweredHouse/ehos-tools \
  'refs/tags/ehos_design-vX.Y.Z' 'refs/tags/ehos_design-vX.Y.Z^{}'
# an annotated tag prints two lines: the commit is the one ending in ^{}; a lightweight tag
# prints one, which is the commit
```

`ehos_app` writes this dependency, at this commit, into the applications it generates.

A `sparse:` dependency keeps its subdirectory, so the files are under
`deps/ehos_design/packages/ehos_design/priv/`.

### With Tailwind and daisyUI, as Phoenix 1.8 generates them

In `assets/css/app.css`, import the layer right after Tailwind's own import, keep daisyUI's themes
off (`themes: false`, as Phoenix writes it), and remove the two `daisyui-theme` blocks Phoenix
writes, which would set daisyUI's colours over the layer's:

```css
@import "tailwindcss" source(none);
@import "../../deps/ehos_design/packages/ehos_design/priv/css/ehos_design.css";
```

Serve the fonts from the application's own origin, in the endpoint, beside Phoenix's
`Plug.Static`:

```elixir
plug Plug.Static,
  at: "/",
  from: {:ehos_design, "priv/static"},
  gzip: false,
  only: ~w(ehos_design),
  cache_control_for_etags: "public, max-age=86400"
```

The fonts' paths carry no version, so they are cached for a day and revalidated by their ETag after
that, rather than on every page load.

The layer names them as `/ehos_design/fonts/<file>.woff2`, and loads nothing from another origin, so
it works under a `Content-Security-Policy` of `default-src 'self'`.

Preload the two faces nearly all text is set in, in the root layout's `<head>`, before the
stylesheet:

```heex
<link
  rel="preload"
  href="/ehos_design/fonts/albert-sans-latin-400-normal.woff2"
  as="font"
  type="font/woff2"
  crossorigin
/>
<link
  rel="preload"
  href="/ehos_design/fonts/albert-sans-latin-500-normal.woff2"
  as="font"
  type="font/woff2"
  crossorigin
/>
```

Without them a browser asks for a font only once it has parsed the stylesheet and laid out text
in it, so a first visit shows the fallback (`-apple-system`, `"Helvetica Neue"`) and then reflows
into Albert Sans. Body text is set at 400; bold text, buttons, table headers and the title classes
(`.eh-display`, `.eh-section-title`, `.eh-h3`) at 500. A page with none of those preloads 500 for
nothing, about 10 KB and a console warning, which is the price of every other page drawing them
right the first time. `crossorigin` is required even on the same origin: fonts are fetched in CORS
mode, and a preload without it is fetched twice. The other faces (`latin-ext`, JetBrains Mono) are
left to load on demand, since a preload a page does not use costs a request and a console
warning. `ehos_app` writes these two links into the layout of an application it generates.

### With plain CSS, or a build of your own

`priv/css/colors_and_type.css` needs nothing but a browser. Import it, or bundle it with esbuild,
declare the fonts with `@font-face` (the layer's declarations can be copied), and serve them or
copy them into your own static files. A package that commits its built assets, as
`eh_os_contract_web` does, can depend on `ehos_design` for its build alone, with
`only: :dev, runtime: false`, so its own hosts never fetch it.

### The components

`EhosDesign.Components` has the listbox's two controls: `picker/1`, a button that opens a list to
choose from, and `combobox/1`, a text field whose list shows what the application found for what is
typed. Each option is a title and an optional subtitle, optionally in groups. Both follow the
WAI-ARIA Authoring Practices' combobox patterns: the focus stays on the control, the arrow keys move
through the list, Enter chooses, and Escape closes it. The module's documentation has the keys and
the attributes.

It also has `outcome/1`, a card that says how something ended: a mark (a lime check, or a coral
cross for `kind={:error}`), a title, one sentence and an optional hint. A page that shows only that
puts it in `<main>` under `<body class="eh-outcome-page">`, after a
`<header class="eh-outcome-header">`.

They need LiveView 1.1 or later, which the package depends on. Import the module where the
application's components are, such as `html_helpers` in `lib/my_app_web.ex`:

```elixir
import EhosDesign.Components
```

Add their hook to the `LiveSocket` in `assets/js/app.js`. The package's hook is colocated, so
LiveView's compiler writes it under the build's `phoenix-colocated/ehos_design`, beside the
application's own:

```js
import {hooks as colocatedHooks} from "phoenix-colocated/my_app"
import {hooks as designHooks} from "phoenix-colocated/ehos_design"

const liveSocket = new LiveSocket("/live", Socket, {
  hooks: {...colocatedHooks, ...designHooks},
  // …
})
```

Their stylesheets come with the layer. The components also use `fieldset`, `label` and a margin
utility around the control, as Phoenix's `<.input>` does; to let Tailwind find them wherever the
application does not use them itself, name the package's templates as a source in
`assets/css/app.css`:

```css
@source "../../deps/ehos_design/packages/ehos_design/lib";
```

A choice sets a hidden input and dispatches `input` on it, so the form's `phx-change` receives it
like any other field. The application keeps what is offered and what is chosen, and passes the
chosen value back, as it does for any input.

## Changing the look

- **One token, or a few.** Override it on `:root` after the import, in a section of your own:

  ```css
  :root {
    --lime: #7dd3fc;
  }
  ```

  The tokens are in the `base` layer, so an unlayered rule wins. A token that differs between the
  themes is overridden in the four places the tokens set it, in their order: on `:root`, under
  `@media (prefers-color-scheme: light)` on `:root`, then under `[data-theme="light"]` and
  `[data-theme="dark"]`, the last two after the media query so that they win by order. Leaving
  out the last one shows the light value to a person who pinned dark on a light system.
- **A look of your own.** Remove the import, turn daisyUI's themes back on (or add your own
  `daisyui-theme`), remove the `Plug.Static` for the fonts and the fonts' preloads, the `@source`
  of the package's templates, and the import of its hooks and `...designHooks` in
  `assets/js/app.js`, and remove the
  dependency. Whatever uses the design system's classes or tokens by name changes with it, such as
  the example page an application generated by `ehosctl init` has at `/design-system`. In such an
  application, keep the comment above the import, as it says: it tells `ehos_app`'s installer not
  to add the design system back.
- **The design system itself.** It is made in Claude Design and shared by a family of products, so
  a refresh never writes to it. Ask in an issue: a maintainer takes it to the design system,
  and it arrives with the next refresh. A maintainer may have an agent make the change there, for
  named files, conditional on each file's etag, but never as part of a refresh (eh-os D-86).

## Refreshing the design system

The tokens and the components' stylesheets are refreshed on request, in one direction, from the
design-system project that `SOURCE.md` names: `colors_and_type.css`, and every file under
`components/`. With Claude Code and the Claude Design MCP server, the `sync-design-system` skill
of this repository (`.claude/skills/sync-design-system/`) does every step below. Without it, a
maintainer with access to the project does them by hand, from each file as Claude Design exports
it:

1. Compare each file's etag in Claude Design with the one in `SOURCE.md`. A file whose etag is the
   same is current. A stylesheet under `components/` that `SOURCE.md` does not list is a new
   component.
2. Take each changed file whole, and check that its size in bytes and lines is what Claude Design
   reports. Whatever is copied by hand or by a tool, take it twice and compare the two byte for
   byte: a size does not catch one character changed for another.
3. In `colors_and_type.css`, remove the Google Fonts `@import` line, and nothing else. A
   component's stylesheet is taken unchanged. If a file now loads anything from another origin,
   or names fonts other than Albert Sans and JetBrains Mono at 400 and 500, stop: that needs a
   decision, and fonts to be added here.
4. Diff each old copy against the new one. For the tokens, list those added, removed and changed
   in each theme; for a component, the classes and states. A token the layer uses, or a class
   `EhosDesign.Components` renders, that is removed or renamed is handled in the same change, and
   is a breaking change for every application that uses it.
5. Replace the copies under `priv/css/`, and rewrite `SOURCE.md`: for each, the new etag, the
   date, the SHA-256 and size as published, and, for the tokens, the SHA-256 as committed. A new
   component's stylesheet is imported by `ehos_design.css` and rendered by a component here.
6. Run `mix check`, and add the change to `CHANGELOG.md` under `## [Unreleased]`: what it asks
   of the next release is a patch for changed values, a minor version for added tokens,
   components, classes or states, and a major one for removed or renamed ones, whose line starts
   with `**Breaking:**`. The version in `mix.exs` stays as it is: it changes only in a release's
   pull request ([releases](https://github.com/EmpoweredHouse/eh-os/blob/main/docs/releases.md)).
7. A font is replaced under a new file name, never in place: its path carries no version, and a
   browser keeps the old file for a day.
8. Once merged, it reaches the consumers with the next release: a pull request of its own sets
   the version and moves the `Unreleased` lines under it, and the tag `ehos_design-vX.Y.Z` on its
   merge commit publishes it. The consumers take it by raising their dependency.

## Development

```sh
mix browser.setup   # once per machine: Playwright and the browser it drives, with Node from npm
mix check
```

Formatting, compilation with warnings as errors, and the tests. The tests check the tokens, the
components' stylesheets and the fonts against the hashes in `SOURCE.md`, that nothing names another
origin, that every token the layer uses is defined and none is redefined, that every font it names
is in the package, and that nothing but the fonts and their licences is where a host serves them
from. They render each component and check its roles, states and classes, and a browser test
(`test/ehos_design/components_browser_test.exs`) drives a page with both through the keyboard and
the pointer, on a LiveView served from `test/support/browser/`.
